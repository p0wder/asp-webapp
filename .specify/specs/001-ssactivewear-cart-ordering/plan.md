# Implementation Plan: SS Activewear Cart & Ordering Workflow

**Input**: Feature specification from `.specify/specs/001-ssactivewear-cart-ordering/spec.md`

## Summary

Augment the existing Ready-to-Order invoice cards on `/orders` with SS Activewear sourcing: each Printavo invoice line item is matched against the SS Activewear catalog by style number; matched items expose an "Add to Cart" action, unmatched items are labeled "Sanmar – Auto Order". A persistent (localStorage) cart aggregates items from multiple invoices. A pre-checkout summary screen groups items by source invoice, surfaces current SS Activewear stock, lets the user adjust quantities or drop short-stock items, and submits a single consolidated order through the existing `/api/place-order` route.

Per clarifications: match strictly by **style number**, persist cart in **browser localStorage**, treat lookup failures as a **"Lookup failed — Retry"** state, show **inline stock warnings** at pre-checkout (do not block submission), and allow **free quantity editing** in the cart.

## Technical Context

**Language/Version**: JavaScript (ES modules) — JSDoc only; no TypeScript (per constitution).

**Primary Dependencies**: Next.js 16.1.6 App Router, React 19.2.3, NextAuth.js 4, Tailwind CSS v4. No new runtime dependencies required.

**Storage**: Browser `localStorage` for cart state. No new server-side storage. Existing Printavo (GraphQL) and SS Activewear REST APIs are read/write integrations.

**Testing**: Manual verification in the dev server (`npm run dev`) + ESLint. The repo has no automated test framework configured; we will not introduce one for this feature (YAGNI). Reproducible manual scripts captured in `quickstart.md`.

**Target Platform**: Web app served from Vercel (Node 18+ runtime for App Router). Desktop and mobile browsers (mobile responsive — see Tailwind `sm:`/`md:` breakpoints already used on `/orders`).

**Project Type**: Web application (Next.js App Router monolith — single repo, no separate backend).

**Performance Goals**: Catalog lookup for one invoice card (typically ≤10 line items) MUST return in under 2 s P95 to keep SC-001 (5 s page-load classification) achievable. Lookup batches are coalesced per invoice card render.

**Constraints**:
- No database — cart lives in `localStorage` only; multi-tab sync via `window.storage` events.
- `testOrder: true` remains hardcoded in `lib/ssActivewear.js#createSSOrder` (do not flip in this feature).
- All API routes must remain thin adapters (constitution V) — cart aggregation/validation logic lives in `lib/`.
- No new third-party deps unless justified.

**Scale/Scope**: Single tenant (Americana Screen Printing). Order page shows ≤4 invoices at a time (`first: 4` in `ready-to-order` query). Cart will typically hold <50 items across <10 invoices in a single ordering session.

## Phase 0: Outline & Research

See [research.md](./research.md). Key decisions reached:

1. **Catalog match implementation** — Use SS Activewear's `?style=` filter (which matches by `styleName`) rather than relying on the hand-curated `STYLE_ID_MAP`. This lifts the cap of "two known styles" and makes the catalog match honest for arbitrary invoice line items. `STYLE_ID_MAP` stays as a fast-path for the pricing endpoint.
2. **SKU resolution** — Invoice line items expose `itemNumber` (style number) + `color` + per-size counts. Each (style, size, color) combination resolves to one SS Activewear variant SKU at the moment of "Add to Cart"; the cart stores SKUs, not raw line-item references.
3. **Cart persistence** — `localStorage` key `asp.cart.v1`; subscribe via `window.addEventListener('storage', ...)` for multi-tab sync; expose via React 19 `useSyncExternalStore` for tear-free updates.
4. **Stock surfacing at checkout** — Re-query SS Activewear when the checkout page mounts, mapping each cart SKU's current `qty` field. Compare to requested qty per line; flag insufficient items inline.
5. **Lookup failure UX** — Per-line-item state machine: `pending → match | sanmar | failed`. A failed lookup shows "Retry"; retries only re-fetch the failed line item, not the whole invoice.
6. **Duplicate-submit / idempotency** — Disable the Submit button while the request is in-flight; rely on the existing route's exception handling for failure replay. (Deferred clarification — no server-side idempotency token introduced in v1; flagged in research.md for future work.)
